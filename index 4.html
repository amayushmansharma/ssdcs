Overview

Diagnose a public repository, generate evidence-backed fixes, and ship them as one reviewable pull request.

The five stages

No account needed to scan
  1. 1

    SCAN

    Repo metadata, default branch, full recursive file tree, and the contents of README / LICENSE / CONTRIBUTING / .gitignore / workflows / manifests.

  2. 2

    FIND

    A declarative rule engine scores the repo 0–100 and lists every problem with the evidence that produced it.

  3. 3

    FIX

    Real file contents generated from templates and tailored to the detected stack — shown as unified diffs.

  4. 4

    REVIEW

    Fork, branch, commit and open a PR with your token — or download a ZIP plus a copyable PR description.

  5. 5

    VERIFY

    Re-run the rules on the patched tree, then poll the real GitHub check-runs for your branch.

House rules

Honesty mode
  • ✔Every finding comes from an actual API response. Nothing is guessed or invented.
  • ✔Errors are reported plainly: bad URL, private/404 repo, rate limit (with reset time), network failure.
  • ✔Verification never simulates a CI result. If checks can't be read, it says so.
  • ✔You review every diff before anything leaves your browser.
  • ✔Demo mode loads a bundled sample dataset, clearly labelled — useful offline or when rate-limited.

Unauthenticated GitHub API access is typically limited to 60 requests/hour per IP. A scan makes multiple requests. See DOCS for token permissions and limitations.

    Deterministic test suite

    Runs entirely in your browser against bundled fixtures. No network, no GitHub calls. These are unit tests — they are not the required live sandbox demonstration.

    ⚑
    Not covered here: live GitHub API authentication, fork creation, PR opening, Actions execution and rate-limit behaviour. Those require a real token and network access, and are exercised only by the live demo — never simulated.

    RepoRescue operating manual

    Run it

    No build step and no backend. Open index.html in a modern browser, or serve the folder with python3 -m http.server 8080 and visit http://localhost:8080. An internet connection is needed for the GitHub API, Google Fonts, the JSZip CDN and the js-yaml CDN. The Tailwind browser CDN is not used and has been removed. Demo mode works without GitHub access.

    Token

    Tokens stay in memory and are sent only to api.github.com. For an existing authorized fork, use a fine-grained token with Contents and Pull requests write permissions; workflows may require additional workflow permissions. Fork creation may need Administration permission. Classic public-repo tokens may also need the workflow scope. Organization policy and token resource-owner restrictions can prevent cross-repository PRs. Never paste a token into generated text.

    Scoring model

    Score = max(0, 100 minus the weights of findings and NOT CHECKED rules). Unknown evidence never earns credit. A score on an incomplete scan is provisional. Comparisons with different unknown checks are not proof of improvement. Each rule's weight is listed below; the first 100 total points are available.

    What is validated

    Every generated file is checked for: path safety (no traversal/absolute paths), duplicate paths, secret-looking strings, JSON parseability, workflow structure (on, jobs, runs-on, steps, a uses or run per step), Markdown structure (H1, balanced code fences), and preservation of the original bytes for modified files. Build/test execution is BLOCKED by design: untrusted repository code is never executed in the browser.

    Two-minute offline demonstration

    1. Click Try the demo. The mode bar says DEMO — BUNDLED DATA — NO GITHUB WRITES. 2. In Find, open the README finding and read its evidence. 3. In Fix, inspect the README diff and selected files; a license choice is separate and never automatic. 4. In Review, read structural validation, not a test-run result. 5. In Verify, the Recorded example, not a live result badge and dashed Demo preview gauge show the baseline and recalculated selected-patch score. The storyline explains which checks would clear and which remain open. The workflow remains Preview only or Skipped; no GitHub PR, CI run, merge or live rescan exists.

    Live demonstration checklist

    1. Fork the repository assigned for the event (its URL is not bundled), then enable Actions. 2. Scan your fork's URL and record its baseline commit, findings and health score. 3. Inspect generated diffs, select files, and read structural validation. 4. With a token scoped for Contents, Pull requests and workflow-file writes, click Create pull request once. 5. Review and merge it yourself on GitHub; never merge a failing workflow just to complete a demo. 6. In Verify, click Rescan merged repository. A verified 5/5 requires an exact match to the PR merge commit, a complete comparable rescan with an actual score improvement, and a successful first attempt of every relevant Actions push workflow on that merge commit. Missing or failed CI and an advanced branch stay unverified. A first attempt is not necessarily the first-ever run; inspect GitHub's run number separately.

    Known limitations

    Licenses: RepoRescue proposes a LICENSE file only after you choose MIT and enter the copyright holder. It does not generate Apache-2.0 text in this build; copy the official text yourself. This is not legal advice.

    Tests: when no test command is detected, RepoRescue gives stack-specific guidance but does not generate test files.

    Only a single repository is supported; organization-wide scans are not implemented. Oversized, skipped and unreadable files are reported as unknown. A truncated tree makes tree-dependent checks unknown. js-yaml parses workflows when the CDN is available, followed by limited structure checks; neither proves execution. Maintainers choose their own license. Browser validation does not run repository code. The demo fixture is not the DevForge sandbox.
